## 1. Overview

This repository contains a comprehensive dataset for malware analysis, featuring 202 processed malware samples and 6,993 corresponding obfuscated variants. The dataset was generated by an analysis pipeline that decompiles, analyzes, and applies 45 distinct obfuscation techniques to each sample.

This dataset is intended for research in malware detection, reverse engineering, and the evaluation of security products against modern obfuscation.

This document provides a comprehensive overview of the malware analysis and obfuscation pipeline, including all input samples, generated obfuscated variants, and detailed descriptions of each obfuscation technique.


### 📊 Key Statistics (v1.0)

* **Input Samples:** 220 (153 `.exe`, 6 `.apk`, 6 `.vbs`, etc.)
* **Processed Samples:** 202
* **Total Obfuscated Variants:** 6,993
* **Avg. Variants per Sample:** ~34.6
* **Obfuscation Techniques:** 45+

## 2. Methodology

The dataset was generated using a multi-stage pipeline:

1.  **Sample Collection:** Malware samples were collected from public repositories and security feeds.
2.  **Static Analysis:** Samples were disassembled and decompiled using **Ghidra**. Metadata was extracted using tools like `pefile`.
3.  **Obfuscation Generation:** A custom engine applied 45+ distinct obfuscation techniques to the decompiled C code and original binaries to generate ~44 variants per sample.
4.  **Dynamic Analysis:** Samples were executed in a custom sandbox to capture runtime behavior (network, file, registry activity).
5.  **Threat Intelligence:** All samples and variants were submitted to **VirusTotal** to gather detection statistics.
6.  **Report Generation:** All static, dynamic, and detection data was consolidated into a single `report_<sample_name>.json` for each sample.

## Methodology

### Data Collection Process

The malware analysis and obfuscation pipeline follows a systematic methodology to collect, process, and generate comprehensive datasets.

#### 1. Sample Collection
- **Source**: Malware samples are collected from various sources including:
  - Research repositories
  - Security vendor feeds
  - Public malware databases
  - Controlled environments
- **Collection Criteria**: Samples are validated for:
  - File integrity (hash verification)
  - File type support (executables, documents, scripts)
  - Safety (contained analysis environment)
- **Time Frame**: Data collection is ongoing, with initial dataset compiled from samples collected between **2025-01-01** and **2025-11-01**

#### 2. Analysis Pipeline Execution

**Tools and Technologies Used:**

##### Static Analysis Tools:
- **Ghidra** (v10.3+): 
  - Binary reverse engineering and decompilation
  - Function extraction and analysis
  - Control flow graph generation
  - Cross-reference analysis
  - Headless analyzer for automated processing
- **pefile** (Python library): 
  - PE (Portable Executable) file parsing
  - Section and import table analysis
  - Rich header extraction
- **objdump**: 
  - Assembly code extraction
  - Instruction-level analysis
- **YARA**: 
  - Pattern-based malware detection
  - Custom rule matching

##### Dynamic Analysis Tools:
- **Custom Sandbox Environment**:
  - Runtime behavior monitoring
  - Network activity capture
  - File system change tracking
  - Registry modification logging
  - Process spawn monitoring
- **Process Monitoring**: 
  - System call interception
  - API call logging
  - Memory analysis

##### Obfuscation Generation Tools:
- **Python cryptography library** (Fernet): Encryption obfuscation
- **Custom obfuscation engines**: 45 different obfuscation techniques
- **UPX**: Executable packing
- **Custom bytecode compilers**: VM-based obfuscation

##### Threat Intelligence Tools:
- **VirusTotal API**: 
  - Multi-engine malware detection
  - Hash-based lookups
  - File submission and analysis
  - Detection statistics collection
- **Custom Threat Database**: 
  - Signature-based attribution
  - Function hash matching
  - MITRE ATT&CK mapping

##### Machine Learning & AI:
- **Transformers Library** (Hugging Face): LLM fine-tuning
- **TinyLlama** (1.1B parameters): Base model for threat analysis
- **LoRA** (Low-Rank Adaptation): Efficient fine-tuning
- **PyTorch**: Model training and inference

##### Reporting Tools:
- **Python libraries**:
  - `json`: Report serialization
  - `matplotlib`: Data visualization
  - `pandas`: Data analysis
  - `jinja2`: HTML template rendering

#### 3. Processing Workflow

**Step 1: File Validation**
- File type detection and categorization
- Hash calculation (MD5, SHA1, SHA256)
- PE header analysis (for executables)
- MIME type verification

**Step 2: Static Analysis**
- Ghidra headless analysis execution
- Decompilation to C code
- Function extraction and hashing
- API call identification
- String extraction
- Compiler fingerprinting

**Step 3: Obfuscation Generation**
- Generate 44+ variants per sample using:
  - Basic obfuscation (encryption, polymorphic)
  - Advanced code transformations (control flow flattening, dead code)
  - Modern techniques (VM-based, self-modifying code)
  - Cryptographic obfuscation
  - API obfuscation
  - ROP gadgets
  - Packing

**Step 4: Dynamic Analysis**
- Execute sample in sandbox environment
- Monitor runtime behavior
- Capture network traffic
- Track file system changes
- Log registry modifications

**Step 5: VirusTotal Integration**
- Submit samples and variants to VirusTotal
- Collect detection statistics
- Defer submissions when rate limits are hit
- Cache results for efficiency

**Step 6: Threat Attribution**
- Extract attribution signals (compiler, strings, APIs, etc.)
- Match against threat intelligence database
- Apply ML attribution model (if available)
- Assign threat actor group

**Step 7: Report Generation**
- Consolidate all analysis results
- Generate JSON reports
- Create HTML visualizations
- Update LLM training dataset

#### 4. Data Quality Assurance

- **Verification**: Each variant is verified to exist on disk
- **Validation**: Report structure validated against schema
- **Completeness**: Missing variants are regenerated automatically
- **Consistency**: Hash-based deduplication of samples
- **Error Handling**: Failed analyses are logged and reported

#### 5. Time Frame

- **Initial Development**: 2024-01-01 to 2024-06-30
- **Data Collection**: 2024-07-01 to 2025-11-01
- **Dataset Compilation**: 2025-11-01
- **Ongoing Updates**: Continuous

## 4. Obfuscation Technique Descriptions

This section provides detailed descriptions of each obfuscation technique implemented in the pipeline.

### 4.1 Encrypted Variants

**Location**: `output_reports/<sample>/encrypted_<sample>`

**Count**: 197 variants

**Description**: 
- Applies encryption to the entire malware payload using the Fernet symmetric encryption algorithm
- Generates a unique encryption key for each variant
- The payload is encrypted and wrapped in a decryption stub
- Makes static analysis impossible without the decryption key
- Used to evade signature-based detection systems

**Technique Details**:
- Encryption Algorithm: Fernet (symmetric encryption)
- Key Generation: Cryptographically secure random key
- Runtime Behavior: Decryption occurs at execution time

---

### 4.2 Polymorphic Variants

**Location**: `output_reports/<sample>/polymorphic_<sample>`

**Count**: 198 variants

**Description**:
- Generates polymorphic versions by randomizing function and variable names
- Changes code structure while maintaining functionality
- Uses random constants, magic numbers, and timing delays
- Each generation produces a unique variant with different signatures
- Evades signature-based detection through code mutation

**Technique Details**:
- Name Randomization: Functions and variables are renamed randomly
- Constant Mutation: Magic numbers and offsets are randomized
- Timing Variations: Random delays introduced to change execution timing
- Structure Preservation: Core functionality remains intact

---

### 4.3 Advanced Variants

**Location**: `output_reports/<sample>/advanced_variants/`

**Count**: 1,360 variants (6.7 per sample)

**Techniques Included**:

1. **Control Flow Flattening** (`control_flow_flattened.c`)
   - Restructures program control flow into a state machine
   - Makes control flow analysis extremely difficult
   - Preserves original program logic while obfuscating structure

2. **Dead Code Insertion** (`dead_code_inserted.c`)
   - Inserts non-executable code paths to confuse analysis
   - Adds fake branches and unreachable code
   - Increases code complexity without affecting functionality

3. **Variable Renaming** (`variables_renamed.c`)
   - Obfuscates variable names with meaningless identifiers
   - Makes code less readable for human analysts
   - Preserves functionality while hiding intent

4. **Function Inlining** (`functions_inlined.c`)
   - Inlines function calls to flatten call hierarchy
   - Makes function boundaries unclear
   - Increases code complexity and analysis difficulty

5. **Instruction Substitution** (`instructions_substituted.c`)
   - Replaces instructions with equivalent sequences
   - Uses different instruction combinations for same operations
   - Evades instruction-level pattern matching

6. **String Obfuscation** (`strings_obfuscated.c`)
   - Encrypts or encodes string literals
   - Replaces plaintext strings with encoded/encrypted versions
   - Hides API calls, URLs, and configuration data

7. **Anti-Debugging** (`anti_debugging.c`)
   - Adds checks to detect debugging environments
   - Includes IsDebuggerPresent() calls and timing checks
   - Terminates execution if debugging detected

8. **Polymorphic Engine** (`polymorphic.c`)
   - Advanced polymorphic transformations
   - Combines multiple obfuscation techniques
   - Generates unique variants each time

---

### 4.4 Code-Based Variants

**Location**: `output_reports/<sample>/code_based_variants/`

**Count**: 1,686 variants (8.3 per sample)

**Description**:
- Applies obfuscation techniques directly to decompiled C code
- Works with real code structure extracted from Ghidra analysis
- Generates 10 different variants using various code transformation techniques
- More sophisticated than template-based obfuscation as it preserves actual code semantics

**Techniques Applied**:
- All techniques from Advanced Variants (see 4.3)
- Additional code-level transformations
- Real function and variable analysis
- Semantic-preserving transformations

---

### 4.5 API Obfuscated Variants

**Location**: `output_reports/<sample>/api_obfuscated_variants/`

**Count**: 510 variants (2.5 per sample)

**Techniques Included**:

1. **API Hashing** (`api_hashing.c`)
   - Replaces API function names with hash values
   - Resolves functions dynamically using hash lookups
   - Evades API name-based detection
   - Uses hash algorithms (CRC32, DJB2, etc.) to compute function addresses

2. **Dynamic Import Resolution** (`dynamic_imports.c`)
   - Loads DLLs and resolves functions at runtime
   - Uses GetProcAddress() instead of static imports
   - Makes import analysis difficult
   - Hides which APIs the malware uses

3. **IAT Hiding** (`iat_hiding.c`)
   - Obfuscates Import Address Table entries
   - Rebuilds IAT at runtime
   - Evades static analysis tools that inspect IAT
   - Makes API dependency analysis harder

### 4.6 VM-Based Obfuscated Variants

**Technique Details**:
- **VM Bytecode Compilation**: Original code compiled to custom instruction set

- **Instruction Mapping**: Each original instruction mapped to VM bytecode operations
- **Obfuscation Level**: Very high - requires reverse engineering the VM itself

**Use Cases**:

### 4.8 Advanced Technique Variants

   - Evades analysis tools that start at main()
   - Can perform anti-analysis checks early

4. **Exception-Based Control Flow** (`seh_control_flow_real.c`)
   - Uses Structured Exception Handling (SEH) for control flow
   - Implements control flow through exception handlers
   - Makes control flow analysis difficult
   - Abnormal control flow paths confuse static analyzers

## 9. Usage and Pipeline

### Processing Flow

1. **Input**: Place malware samples in `input_files/` directory
2. **Analysis**: Run pipeline orchestrator to analyze samples
3. **Ghidra Decompilation**: Extract decompiled C code
4. **Obfuscation Generation**: Generate all variant types
5. **Analysis**: Analyze each variant with VirusTotal and dynamic analysis
6. **Report Generation**: Create comprehensive JSON reports
7. **Output**: Variants stored in `output_reports/<sample>/`

### Command Examples

```bash
# Process all samples
python malware_analysis_pipeline/pipeline_orchestrator.py

# Process single sample
python malware_analysis_pipeline/pipeline_orchestrator.py input_files/sample.exe

# Generate missing variants
python malware_analysis_pipeline/complete_obfuscation.py
```

### Special Values and Codes

#### Missing/Error Values

- **"N/A"**: Field not applicable or data not available for this sample
- **"Unknown"**: Value could not be determined (e.g., attribution unknown)
- **"Static analysis failed"**: Static analysis could not be performed (Ghidra failure, etc.)
- **"VirusTotal analysis skipped"**: Analysis was skipped (no API key, rate limit, etc.)
- **Error objects**: Contain `"error": "description"` key with error message

#### Boolean Values

- `true`: Feature detected/present
- `false`: Feature not detected/absent

#### Integer Ranges

- **File sizes**: 0 to maximum file system size (typically 2^63 - 1 bytes = ~9.2 exabytes)
- **Hash counts**: 0 to 2^32 - 1 (4.3 billion)
- **Complexity metrics**: 0.0 to practical maximum (~1000 for extreme cases, typical range 1-100)
- **VirusTotal scans**: 0 to ~70 (current number of engines on VirusTotal)

#### String Formats

- **Timestamps**: "YYYYMMDD_HHMMSS" format (e.g., "20251101_102707")
- **Hashes**: Lowercase hexadecimal strings
  - MD5: 32 characters (e.g., "f2b7074e1543720a9a98fda660e02688")
  - SHA1: 40 characters (e.g., "1029492c1a12789d8af78d54adcb921e24b9e5ca")
  - SHA256: 64 characters (e.g., "4ea1f2ecf7eb12896f2cbf8683dae8546d2b8dc43cf7710d68ce99e127c0a966")
- **File paths**: Forward slashes (/), relative to project root (e.g., "output_reports/000.exe/000.exe.c")
- **IP addresses**: IPv4 (e.g., "192.168.1.1") or IPv6 format
- **Ports**: Integer as string, range 0-65535 (e.g., "443", "8080")

#### MITRE ATT&CK Technique IDs

Common technique IDs found in reports:
- **T1055**: Process Injection
- **T1059**: Command and Scripting Interpreter
- **T1047**: Windows Management Instrumentation
- **T1105**: Ingress Tool Transfer
- **T1021**: Remote Services
- **T1566**: Phishing
- **T1547**: Boot or Logon Autostart Execution
- Format: "T" followed by 4 digits (T0001-T9999)

#### Threat Actor Groups

Common attribution values:
- **"APT28"**: Fancy Bear / Sofacy
- **"Lazarus"**: North Korean threat group
- **"Unknown"**: Could not be attributed
- Format: String, typically uppercase acronyms or group names

## 10. Conclusion

This pipeline provides a comprehensive framework for malware analysis and obfuscation variant generation. With 6,993 variants generated across 202 samples, it demonstrates the effectiveness of various obfuscation techniques in evading detection and complicating analysis.

Each obfuscation technique serves a specific purpose:
- **Basic techniques** (encryption, polymorphic) provide quick signature evasion
- **Advanced techniques** (control flow, dead code) complicate static analysis
- **Sophisticated techniques** (VM-based, self-modifying) require specialized analysis tools

The generated variants serve multiple purposes:
- Security research and testing
- Detection system evaluation
- Analysis tool development
- Threat intelligence gathering
- Academic research
